# 콤파 프롬프트 버전 관리

## 관리자에서 새 버전을 적용하는 순서

1. 관리자 → 콤파 대화·평가 → 프롬프트 관리에서 현재 적용 중인 버전을 확인한다.
2. 현재 버전의 이름을 누르면 답변 지침을 확인할 수 있다. `복사`를 누르면 현재 본문으로 새 버전 입력을 시작한다.
3. 새 버전명(예: v2), 변경 설명, 답변 지침 전체를 입력하고 등록한다. 버전명은 영문·숫자·마침표·밑줄·하이픈으로 40자, 설명은 500자, 지침은 16000자 이내다.
4. 등록만으로 적용되지는 않는다. 본문을 확인한 뒤 해당 버전의 `적용`을 눌러 전환한다.
5. 동일한 예상 질문을 직접 입력해 검증한다. 추천 질문·용어 클릭은 고정 답변이므로 이 테스트에 쓰지 않는다.
6. `평가 보기`를 누르면 대화·평가 기록의 검색창에 해당 버전명이 채워진다. 검색창에서 `v1`, `v1 SUV`처럼 버전 또는 버전+질문을 검색할 수 있고, 질문·회원 닉네임 검색도 지원한다. 카운팅 줄에 실제 조회 버전과 검색 결과 전체 평가 수를 표시하며 페이지 이동 시 집계는 유지한다. 답변 상세에서 버전·제공사·모델을 확인한다.
7. 문제가 있으면 이전 버전의 `적용`을 눌러 돌아간다. 과거 답변의 버전과 평가는 바뀌지 않는다.

버전명은 자동으로 증가하지 않으며 새 버전을 등록할 때 정한다. 등록된 버전 본문은 화면에서 수정·삭제하지 않는다. 지침 수정은 항상 새 버전 등록으로 남긴다.

## 버전을 올릴 때 무엇을 바꿔야 하나

| 바꾸려는 내용 | 작업 | 재시작·배포 |
|---|---|---|
| 답변 길이, 말투, 설명 형식, 답변 범위, 자료를 다루는 규칙 | 관리자에서 새 프롬프트 버전 등록 후 적용 | 이 기능이 배포된 뒤에는 필요 없음. 다음 AI 요청에서 DB의 현재 적용 버전을 읽음 |
| 서비스 기능 설명, 용어의 뜻 등 사실 자료 | `back/src/main/resources/chatbot/knowledge/service-guide.md`, `vehicle-terms.md` 또는 설정된 자료 위치 수정 | 기본 구현은 시작 시 자료를 읽으므로 Spring 재시작 필요. 운영은 변경된 자료 배포도 필요 |
| Gemini/GPT 제공사나 모델 | 기존 환경변수 `CHATBOT_PROVIDER`, `GEMINI_MODEL`, `OPENAI_MODEL` 설정 변경 | Spring 재시작 필요 |
| 검색 방식, 개인 정보 첨부 방식, DB 조회 기능, 새로운 API 연동 | 관련 Java 코드·설정 구현 | 코드 검증 후 배포·재시작 필요. 프롬프트만 작성해도 없는 기능이 생기지는 않음 |
| 화면의 추천 질문·용어 클릭 고정 답변 | `ChatGuideAnswers.java` 및 관련 질문 정의 수정 | 배포·재시작 필요. 프롬프트 버전과 별개 |

새 버전을 DB에 INSERT만 해도 적용되지는 않는다. 관리자 화면의 등록·적용 API를 사용하는 것을 권장한다. 현재 적용 상태가 전환되어야 다음 AI 요청에 반영된다. 직접 SQL로 바꿀 경우에도 기존 버전 본문을 덮어쓰지 않고 새 행 등록 후 트랜잭션 안에서 적용 상태를 전환해야 한다. 새 버전마다 마이그레이션이나 Java 코드 수정은 필요하지 않다.

기존 `prompts/chatbot-system.st` 파일은 혼동을 줄이기 위해 삭제했다. 런타임 답변 지침의 원본은 DB다. 최초 설치 때 V32 마이그레이션이 초기 지침을 v1으로 등록하므로 이 파일이 없어도 설치·실행할 수 있다.

## 저장 구조와 비교 기준

- `chatbot_prompt_versions`: 버전명·본문·변경 설명·작성자·등록 시각·현재 적용 상태·최근 적용 시각. 고유 키로 버전명 중복과 복수 버전 동시 적용을 막는다.
- `chatbot_messages.prompt_version_id`: AI 요청에서 실제 읽은 버전을 저장한다. AI 응답을 기다리는 동안 관리자가 버전을 전환해도 시작할 때 사용한 버전을 기록한다.
- `chatbot_feedback`: 기존 좋아요·싫어요 기록을 답변 ID로 연결한다. 평가 취소·변경은 다음 조회 집계에 반영된다.
- V33은 사용자 요청에 따라 버전 기능 도입 전 AI/데모 답변 중 버전이 비어 있는 항목을 v1으로 분류한다. 과거 실행 지침을 역으로 검증한 결과를 뜻하지는 않는다. 이미 다른 버전이 지정된 답변은 유지한다. 고정 답변은 프롬프트를 사용하지 않아 NULL이며 버전별 통계에서 제외한다.
- 긍정 비율 = 좋아요 / (좋아요 + 싫어요). 평가 참여율 = (좋아요 + 싫어요) / 해당 버전의 AI 답변 수. 분모가 0이면 수치 대신 `—`를 표시한다.

평가 집계는 성공하여 저장된 AI 답변만 대상이다. 실패한 AI 요청·지연시간·토큰 사용량을 측정하는 실험 시스템은 이번 범위에 포함하지 않는다. `최근 적용 시각`은 마지막 전환 시각이며 모든 활성화 이력의 타임라인은 아니다.

프롬프트 버전은 참고 자료 버전과 다르다. 현재 기능은 검색된 문서 내용·자료 버전을 답변마다 별도 보존하지 않는다. 따라서 같은 프롬프트라도 자료나 모델이 바뀌면 답변이 달라질 수 있다. 비교 검증에서는 모델·자료·질문·대화 맥락을 동일하게 맞추고, 새 대화에서 같은 질문 묶음을 사용한다. 개인 결과가 첨부되는 제공사는 회원 조건도 맞춘다. 사용자 좋아요가 많다는 사실만으로 답변의 사실성이 입증되는 것은 아니므로 관리자가 실제 답변과 근거도 검토한다.

## 최초 적용과 검증

V32는 새 테이블과 메시지 연결 컬럼을 만들고 v1을 적용 상태로 등록한다. 기존 메시지·평가를 삭제하지 않는다. V33에서 별도로 요청된 기존 AI 답변의 v1 분류를 수행하며 고정 답변과 사용자 메시지는 제외한다. 팀원·운영 서버에는 소스와 마이그레이션을 함께 배포하고 정상적인 Flyway 시작 절차로 적용한다. 기존 마이그레이션 파일은 수정하지 않는다.

로컬 검증: 프롬프트 전환 중 답변의 버전 고정·이전 버전 재적용·없는 버전 적용 거부·동시 적용 DB 제약·버전명 중복 거부·버전별 평가 집계·고정/과거 답변 제외·평가 취소·버전/질문 검색을 MySQL 격리 테이블에서 검사했다. 검증 테이블은 종료 후 제거한다. 테스트는 `PROMPT_TEST_DB_PASSWORD`를 지정한 경우에만 로컬 MySQL에서 실행하며 별도 요청 없이 커밋하지 않는다.
